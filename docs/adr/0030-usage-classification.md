# ADR-0030: Usage classification, because usage IS the recommendation

**Status:** Accepted
**Date:** 2026-09-10
**Slice:** usage accuracy (Part A) + the JS weak-RNG taint sibling (Part B)
**Depends on:** ADR-0004 (`usage: unknown` at keygen, and the promise to refine
it), ADR-0026 (the annotation mechanism and the identity-merge argument),
ADR-0028 (which owed Part B), ADR-0029 (`usage` is identifying)

## Context

`usage` decides the post-quantum target:

```
RSA for SIGNING        -> ML-DSA  (FIPS 204)
RSA for KEY TRANSPORT  -> ML-KEM  (FIPS 203)
```

So a wrong usage is a wrong migration, which is the one output an operator
acts on. Two things were wrong.

**The packs reported verification as signing.** The Python and JS JWT rules
matched `jwt.decode` and `jwt.verify` and carried `usage: sign` — a bug this
project introduced in ADR-0028 when it added the verify patterns to the
existing sign rules. Every token VERIFIER in an estate was recommended a
signing migration, and verification is the side that must move *first*: nothing
can accept an ML-DSA token until its verifier does.

**Nothing consumed usage anyway.** Auditing the packs turned up the more
awkward fact: **no policy rule conditioned on `usage` at all.** The RSA action
was one string listing every option and telling the reader to choose. Correct,
and not actionable — and it meant improving usage would have changed nothing
visible.

## Decision — Part A

### 1. The recommendation branches on usage (a PACK change, not an engine one)

`quantum-shor-broken-asymmetric` keeps its score of 40 and loses its action.
Three new rules score **zero** and carry the action instead:

| usage | rule | target |
|---|---|---|
| `sign`, `verify` | `quantum-target-signature` | ML-DSA (FIPS 204) |
| `key-transport`, `key-exchange`, `decrypt` | `quantum-target-kem` | ML-KEM (FIPS 203) |
| anything else | `quantum-target-unknown-usage` | both, and says why |

The engine is untouched: it already exposed `usage` as a fact and already
collected `action` from fired rules. What was missing was rules to condition
on it. Scoring zero is what keeps this a recommendation change rather than a
risk change — the 40 still comes from one place.

The signature action also says *migrate the verifiers first*, because a signer
that moves ahead of its verifiers breaks the service.

### 2. API-level usage, where the call names it

New rules across all four packs, for the usages that were **absent entirely**:

* **`verify`: zero rules in any pack before this slice.** Now `jwt.decode` /
  `jwt.verify` split out per family, plus `rsa.VerifyPKCS1v15`,
  `ecdsa.Verify`, `Signature.initVerify`, `$PUB.verify(...)`.
* **`key-transport`: only Java had one.** Now `$PUB.encrypt(...OAEP)`,
  `rsa.EncryptOAEP`, `crypto.publicEncrypt`, and — the interesting one —
  `Cipher.WRAP_MODE`. Java's transformation string is *identical* for wrapping
  a key and encrypting data, so the init mode is the only signal there is.
* **`key-exchange`: absent from Python and JS.** Now `$KEY.exchange(ec.ECDH())`
  and `crypto.createECDH`.

A Python RSA key-wrapping site previously produced **no finding at all** — the
artefact that most needs ML-KEM was the one missing from the inventory.

### 3. Use-site refinement (Python), as an ANNOTATION

ADR-0004 fixed `usage: unknown` at every keygen — correct, because a fresh RSA
key may sign or transport — and said the correlator would refine it from the
use site. Nothing did, for six ADRs.

`knowledge/rules/python/usage_refinement.yaml` carries `annotates: usage`,
extending ADR-0026's mechanism to a second kind. Each rule matches the
**keygen** and requires the use site in the same function via `pattern-inside`,
so semgrep reports at the keygen line — which is exactly where the finding to
annotate already is, and is why the existing `(path, line)` join works
unchanged.

Three properties are deliberate:

* **It only ever refines an `unknown`.** A rule that read the usage off the API
  is better evidence, and a refinement that overrode it would let a use site
  rewrite a fact the call itself stated.
* **It changes the bom-ref**, because `usage` is identifying (ADR-0029). That
  is the point: a signing key and a transport key generated by identical calls
  in different functions ARE different artefacts with different migrations.
* **Two refinements on one keygen resolve deterministically** — first in sorted
  rule order. A key that both signs and wraps is a real and bad pattern;
  reporting one of two true usages is a limit, reporting a different one each
  run would be a determinism break.

### 4. Unknown stays unknown

A keygen with no visible use site matches nothing and keeps `usage: unknown`.
Intra-procedural analysis cannot see through a function boundary, and a guessed
usage is a confidently wrong migration target on a real key. The pack's
`quantum-target-unknown-usage` rule then gives the agnostic advice *and says
ECDAT could not determine the usage and will not guess* — which is a better
output than a plausible wrong answer.

## Decision — Part B

`js-math-random-dataflow` (`mode: taint`): `Math.random()` reaching a key, MAC
or token sink. ADR-0028 owed this and deliberately did not translate the Python
rule, because the identity-merge argument had to be re-made for JS sinks.

**Both rules ship; neither is a superset.** The name-scoped rule catches
`const token = Math.random()` with no sink in the same function — taint is
intra-procedural, so a value returned to a caller is invisible to it. The taint
rule catches the flowing-but-badly-named case. Where both fire they agree on
every identifying field, so they carry one identity and the normaliser folds
them into a single component; a test asserts the single component, and the
`flags` must stay equal between the two or `params.flagged` would split the
identity and double-report the same weak key.

## Consequences

**Good.**

- A JWT verifier is no longer recommended a signing migration.
- `verify`, `key-transport` and `key-exchange` are reported where the API names
  them, across four packs. RSA key wrapping in Python is inventoried at all.
- A Python keygen refines to `sign` or `key-transport` from its use site, and
  stays `unknown` when there is none.
- The recommendation is now one target instead of three options — and still
  three options where the usage is genuinely unknown.
- Part B closes ADR-0028's owed item with the double-report asserted, not
  assumed.

**Costs and limits.**

- **Use-site refinement is PYTHON-ONLY.** Go, JS and Java need the same
  `pattern-inside` shapes against their own keygen and use-site APIs. Not
  written, not faked.
- **It is INTRA-PROCEDURAL.** A key generated in a factory and used by its
  caller — the common shape in real code — stays `unknown`. Semgrep Pro's
  interprocedural analysis is the fix.
- **`java-signature-verify` reports `algorithm: unknown`.** The algorithm was
  chosen at `Signature.getInstance` and `initVerify` only sets the direction;
  the usage is the fact the rule adds. Joining the two calls is use-site
  refinement for Java, which is not built.
- **The Java WRAP_MODE rule reports `RSA` unconditionally.** `Cipher.WRAP_MODE`
  says the usage but not the algorithm, and RSA is the overwhelmingly common
  case rather than the only one — an AES key-wrap would be mislabelled.
- **A key used for two things reports one usage** (§3).
- **Inserting rules into `quantum.yaml` silently detached a `verified` flag.**
  The pack's layout let a rule's `verified:` block sit after a comment
  introducing the *next* rule; inserting between them moved the flag onto the
  wrong rule and made `quantum-shor-broken-asymmetric` provisional, which
  dropped its score to zero. Caught by the suite, not by review. The block is
  now attached directly to its rule, but nothing structurally prevents the same
  mistake — a lint that asserts every rule owns its own `verified`/`source`
  would.
